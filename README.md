# 巨鲸追踪与宏观共振仪表盘（WhaleTracker）

个人使用的加密宏观 + 巨鲸仓位聚合仪表盘。前端 Vue 3，后端 Express，数据缓存 5 分钟。

## 方案是否可行

**可行，适合作为个人仪表盘。** 前后端分离、文件缓存、腾讯云轻量部署、月成本远低于 200 元，这些判断都成立。但原方案有几处不改会空转，代码里已经按下面方式修正。

### 必须正视的缺口

1. **预设巨鲸是 Hyperliquid 合约交易员，不是普通链上转账地址。**  
   `cryptocurrency.cv/api/whale-alerts` 给的是全网大额转账，**不会**告诉你 `58bro.eth` 现在做多还是做空。左栏「当前方向」如果只靠 whale-alerts，会永远是观望。  
   **处理：** 后端同时请求 Hyperliquid 公开 Info API（`clearinghouseState` + `userFills`），用净仓位判断做多 / 做空 / 观望，成交列表优先展示这些地址 ≥ 10 万美元的 HL 成交。

2. **ENS 名称无法直接过滤交易。**  
   接口返回的是 `0x` 地址。配置文件增加了 `address` 字段。已填入：
   - `58bro.eth` → `0x418AA6Bf98a2b2BC93779f810330d88cDe488888`
   - `pension-usdt.eth` → `0x0ddf9bae2af4b874b96d287a5ad42eb47138a902`
   - `回撤低b0d2` 方案里只有截断地址 `0x0925…32b0d2`，默认关闭，请在「配置地址」里补全后再启用。

3. **`cryptocurrency.cv` 并非永远免费可用。**  
   文档写免 Key，但 `whale-alerts` 在部分环境会返回 **402**。  
   **处理：** 自动尝试 `fcn.dev` 同源接口；失败时仪表盘仍可用 HL 仓位/成交 + 新闻，并在顶部给出警告，不会整页崩溃。

4. **金十快讯需要请求头。**  
   `flash-api.jin10.com/get_flash_list` 没有 `x-app-id` / `x-version` 经常 502。后端已带上公开站点使用的请求头，并增加 CryptoCompare 新闻兜底。金十是非官方接口，随时可能失效，不要当成生产 SLA。

5. **共振信号只能是「人工宏观判断 × 巨鲸仓位方向」。**  
   输入框不会做 NLP。你选偏多/偏空后，前端统计 ≥ 2 个已启用巨鲸方向一致才亮横幅。这和方案里的手动模式一致，不要误当成自动宏观解读。

### 成本

腾讯云轻量 99 元/年套餐 + 可选域名，月均远低于 15 元，也远低于 200 元上限。没有付费 API Key。

## 本地运行

需要 Node.js 18+。

```bash
# 后端
cd whale-tracker-backend
npm install
npm run dev

# 前端（另开一个终端）
cd whale-tracker-frontend
npm install
npm run dev
```

浏览器打开 http://localhost:5173  
Vite 已把 `/api` 代理到 `http://localhost:3000`。

## 交付功能

- 巨鲸仓位方向 + 大额成交/转账表格
- 加密新闻与金十快讯聚合，关键词高亮
- 手动宏观方向 × 巨鲸共识共振横幅
- 配置弹窗增删监控地址、关键词
- 深色 / 浅色主题
- 打开页面拉取数据，之后每 5 分钟刷新；缓存超过 5 分钟显示「数据已过期」

不包含：自动交易、多用户登录、RSI/MACD。

## 巨鲸同步改造（2026-10-05）

本节说明当前巨鲸模块，前面早期版本的定时刷新说明不再适用于该模块。

- 后端独立采集，SQLite 是持久数据源；事务成功后才更新内存状态并发布消息。JSON 文件仅作兼容镜像。
- 页面通过 `GET /api/whales/bootstrap` 一次取得监控名单、仓位、汇总、最近 100 条异动及 `epoch/seq`。巨鲸列表本地筛选排序，无需逐页下载。
- 浏览器向 `/realtime` 发送 `resume`，先补齐快照之后的事件，再接收 `stateCommit`；重复序号忽略，序号缺口、日志过期或服务重启会重新拉取快照。部署应保持单个 Node 服务进程；多实例需要共享事件日志，当前实现不支持跨实例游标。
- 实时事件按 ID 更新实体；空仓隐藏但保留身份，新开仓重新出现。异动筛选仍通过服务器查询，每次最多显示 100 条，HTTP 结果不能覆盖更新的 Socket 状态。
- 成交按“巨鲸 + 原始成交 ID”幂等入库。原子成交金额与展示聚合金额分离；旧 REST 返回不能覆盖之后已收到的仓位。
- WS 覆盖活跃地址；所有监控地址另做连续 REST 成交补采。默认每 5 秒轮询一个地址，200 个地址一轮至少约 17 分钟，限流和请求耗时会进一步增加间隔，并非所有地址都能秒级更新。
- `WHALE_FILL_CAPTURE=0` 可关闭连续成交补采；原来的 `FILL_BACKFILL=0` 不再控制它。保留 `FILL_BACKFILL_INTERVAL_MS`、`FILL_BACKFILL_DAYS`、`FILL_BACKFILL_RATE_LIMIT_MS` 配置。窗口不完整或失败不会推进覆盖水位。
- 新提醒需要服务器标记、成交时间在 120 秒内且浏览器完成同步；断线回放与历史补采不重放提醒。历史数据未做自动金额修复。
- 配置和破坏性维护操作要求管理员登录；旧 `POST /api/whales/alert-history` 已停用，浏览器不再提交事实数据。

验证命令（各自目录运行）：后端 `npm run test:whale-sync`；前端 `node src/utils/whaleState.test.cjs` 与 `npm run build`。CI 在部署前执行这些检查。打包仍使用 `node whale-tracker-backend/scripts/sync-deploy.js`。

历史数据只读检查：后端目录运行 `node scripts/audit-whale-data.js --db <数据库绝对路径>`。输出仅标记待核对记录，不自动删除、除算金额或重建历史。上线需同时更新前后端并重启后端；尚需进行真实浏览器、线上网络与长期采集验证。

## 计算与内存优化第一阶段（2026-10-08）

- 方向集中度、新鲜度统计采用迭代求极值，避免大规模地址集合展开为函数参数而触发调用栈溢出。
- 共振输入在一次迭代中完成筛选和去重，减少重复输入及无关输入的临时数组；完整金额、次数和固定合并窗口保持原规则。后端共振文件由前端工具源码生成，修改后执行 `node whale-tracker-backend/scripts/build-resonance-engine.js`，可加 `--check` 校验同步。
- 待发布增量默认最多 5000 个条目、估算 4 MiB，单次提交消息最多 4 MiB。超过预算时旋转 epoch 并发布 `resyncRequired`；浏览器重新 bootstrap，SQLite 中的成交和仓位不受影响。超限同步不重放历史提醒。
- 公共 WebSocket 的 4 MiB 缓冲预算包含本次待发送消息的 UTF-8 字节；慢客户端关闭连接后通过快照和游标恢复。
- `/api/data/monitor` 新增 `runtime`：进程内存字段以字节计，事件循环延迟 p95/max 以毫秒计，统计范围为监控模块启动以来；没有延迟样本时返回 null。

验证仍走后端 `npm run test:whale-sync`、前端状态测试与 `npm run build`。新增覆盖：15 万地址、故障积压、超大消息、替换/删除容量核算与发送缓冲边界。该阶段没有延长统计缓存 TTL，也未修改七天观察算法。

## 计算隔离第二阶段（2026-10-08）

- 七天单地址观察和集体观察改由一次一个独立 Node 子进程计算，V8 老生代堆上限 256 MiB，计算超时 120 秒；这是子进程的堆限制，不是整机或总 RSS 上限。API 主进程继续采集和提供最近已提交的结果。
- 子进程只读事实库，将结果写到专用临时 SQLite 文件；IPC 仅传任务参数与成功/失败状态。主进程每批导入 256 条证据并让出事件循环，最终以短事务一起提交汇总、证据指针和任务确认。无变化的结果保留原证据，旧数组格式及第二版共享证据仍可读取。
- 数据库触发器维护输入及观察汇总版本。计算期间新增、修正或删除相关事实，旧结果会被拒绝，持久任务保留待重试；停止任务也会取消正在导入的结果。失败和过期任务轮转到队列后方，最近完整结果仍可读取。
- `/api/data/monitor` 新增 `observationCompute`，包含当前任务、待算地址/币种数、最近耗时、错误和过期/失败次数。证据清理分批执行，保护正在导入的证据；正常结束会删除临时库，主进程被强制终止可能留下系统临时文件。
- 本阶段保持观察规则、金额口径、证据顺序与哈希，仍对七天窗口完整重算。观察结果有排队、计算与导入耗时；持续变化的活跃地址可能反复重试。成交入库和实时事件通道保持原流程，不能将计算隔离解释为所有观察均可秒级更新。下一阶段需要增量计算，以改善吞吐和积压。

后端回归：`node scripts/test-whale-sync.js`（等同 `npm run test:whale-sync`）。新增独立进程结果对照、修正/新增竞争、分批导入可见性、清理保护、取消、超时恢复和失败任务公平性测试。可在后端运行 `node scripts/benchmark-observation-compute.js 6000`，它始终创建临时数据库，不读取真实库；本机一次合成测试产生 98 个观察和 129902 条证据链接，主线程最大延迟从约 883 ms 降到 70 ms，整体耗时从约 0.87 秒增加到 6.34 秒。该测试衡量隔离效果及其导入代价，不代表生产延迟承诺。

部署打包清单已包含两个计算进程文件；本地修改尚未部署。一次监控测试初始化了本地数据库的新表和触发器，随后已补齐该测试的临时数据库隔离；历史成交未清理或重算。上线仍需同时更新运行文件并重启主服务；当前证据读取需兼容第三、第四版格式。尚未完成真实浏览器、线上网络与长期采集验证。

## 证据增量复用第三阶段（2026-10-08）

- 新生成的证据使用第四版格式：每 128 条有序证据组成不可变内容块，块保存原证据行的哈希。汇总仍保留原来的整段证据 SHA-256、数量和顺序；HTTP 分页最多访问所需的一至两个块，旧数组、第二版和第三版格式仍可读取。
- 追加数据时复用完整块，仅写入新的证据行和改变的尾部块。汇总及块指针仍通过版本校验后原子提交，正在导入的块在发布前被保护，取消任务的链接与成功提交后被替换的链接都分批回收。避免持续追加产生垃圾的速度超过每分钟清理预算。
- 子进程对共享证据行只序列化、写入一次。主进程直接分批迭代去重后的证据行，避免展开所有重叠块构造大的临时集合。集体观察按页读取原触发时点以前的证据，不再解码后续 24 小时跟踪中不会进入集体金额的记录。
- 本阶段完成的是证据存储与导入的增量复用。七天观察会话仍由原规则完整重算，历史修正、乱序、同时间戳衔接和反转判断没有通过裁剪历史简化。队列、外部采集速度及高频更新导致的重试仍可能影响实时性，尚未实现观察引擎的完整增量状态机。

回归新增跨块分页、增量块复用、历史修正、乱序补录、删除、清理保护、旧格式兼容及集体观察全历史对照。运行 `node scripts/test-whale-sync.js`。

可重复基准：`node scripts/benchmark-observation-compute.js 6000`，始终使用临时库。一次本机测试的 98 个观察原本有 129902 条证据链接，新格式用 1047 条块链接表示相同证据；独立计算和导入约 515 ms，主事件循环最大延迟约 55 ms。追加一条成交约 300 ms，主循环最大延迟约 12 ms，仅新增一条证据行和 24 个尾部块。第二阶段同规模历史测量为约 6.34 秒，机器负载会影响这些数字。基准对照了完整重算的汇总和证据哈希，不代表线上延迟承诺。

第三阶段的测试和基准均使用隔离临时数据库，本阶段没有部署或打开真实数据文件执行迁移。部署回退必须保留第四版读取能力，或恢复升级前的数据库备份。

## 优化审查后的修复（2026-10-08）

本节更新上述第二、第三阶段的提交校验和清理行为。

- 单地址结果提交后立即发布，不再等待集体观察成功。集体计算失败保留最近结果并显示独立错误，重试至少间隔 10 秒；服务重启时先发布持久结果，再开始计算。
- 严格晚于已有成交最大时间的追加不会使完整输入批次失效。每次提交记录输入版本、窗口时间及最后成交时间；有后续输入时保留持久任务，页面显示覆盖时间和待更新提示。历史修正、乱序或同时间戳插入、删除仍使旧批次失效，较旧批次也不能覆盖已提交的新版本。这保持每个完整批次的金额、证据和汇总一致，但观察仍有排队和完整七天重算耗时。
- 证据引用的全局扫描移到只读子进程，API 主进程仅按每批 256 条应用候选删除，每类候选最多 5000 条。引用版本在计划生成和各批删除间校验；若出现新引用或导入中的保护标记，剩余删除中止，下一轮重新扫描。主进程过期成交、汇总清理各限制为 500 条，避免单次无限删除。
- 集体观察测试固定在完整小时内生成成交，消除跨整点时金额被分桶后偶发失败的问题。新增持续追加、旧批次回退拒绝、修正/删除竞争、清理期间新增引用、集体失败及重启失败恢复测试。

验证：后端 `node scripts/test-whale-sync.js` 全部通过（135 个 Node 测试及脚本断言）；前端状态测试 11 个通过，`npm run build` 通过，仍有原有大文件分包警告。所有修复测试使用临时数据库，本次未部署，也未打开真实数据文件执行迁移。

压力基准：后端运行 `node scripts/benchmark-observation-compute.js 6000 --gc-stress`。本机一次测试中，独立计算和导入约 609 ms、主循环最大延迟 38 ms；追加一条成交约 403 ms、最大延迟 30 ms；1536000 条有效证据引用的清理扫描约 614 ms、主循环最大延迟 11 ms。基准校验汇总与证据哈希相同、有效引用未被删除；数字受机器负载影响，不代表线上时延保证。

## 方向统计与共振读取故障排查（2026-10-08）

线上只读检查时，方向统计与共振接口均返回 200；运行监控记录过约 33 秒的主线程最大阻塞，超过浏览器方向统计 15 秒、共振 20 秒的请求超时。当前证据支持间歇性超时的解释，尚未取得用户报错当时的浏览器请求记录，不能把全部失败都归为同一原因。

- 修复每分钟历史清理的扫描上限：先按 `(time,id)` 游标选取有限候选，再检查持仓保护；原来的过滤后 `LIMIT` 只限制删除数量，仍可能扫描大量保留历史。新增扫描及持仓匹配索引，游标在事务成功后推进；一轮扫描结束后重新检查之前保留的记录，持仓关闭后仍可清理。默认每类最多扫描 500 条，历史保留规则与成交统计口径不变。
- 浏览器对统计 GET 的超时、网络中断及 502/503/504 只额外重试一次，同查询继续共用请求；不重试参数、认证、限流或计算错误。失败提示区分原因，共振可直接点击重试，无需切换时间范围。后端监控保存两类接口的实际计算错误，便于区分超时和计算异常。
- 本地真实库只读查询对照：旧事件清理候选查询约 4172 ms；新查询扫描首批 500 条约 12 ms，其中全部受持仓保护。这是单批扫描对照，不表示两者在相同时间内完成全部清理。本次没有修改真实事实数据，也没有发布到线上。

验证增加保留历史超过扫描预算、同时间戳推进、持仓关闭后回收和有限重试测试。前端新增验证命令 `node src/utils/statisticsRead.test.cjs`，已加入部署前检查；上线需更新前后端并重启后端，之后仍应核对阻塞峰值与失败请求。

## 方向与共振后台预计算（2026-10-08）

本节替换上述两类接口的“请求触发统计 + 3 秒缓存”实现。

- 独立 Node 子进程从只读 SQLite 快照生成方向统计的 15m/1h/4h/24h 结果和共振的 2/4/6/12/24 小时结果。事实分类、反转拆分、金额、合并窗口、多空主信号选择及币种别名匹配继续使用原算法；共振预先生成各币种信号，请求时仅筛选完成的信号并选择主信号，不读取成交或重新扫描。
- 成交及巨鲸快照变更由数据库触发器推进统计输入版本。后台每秒检查，计算启动至少间隔 5 秒；无数据变化也在统计覆盖时间达到 10 秒后重新推进窗口。同一个统计 worker 同时只运行一个子进程，突发更新合并为下一批；计算期间新增、修正、补录或删除事实会显示 `pendingUpdates`，下一批完整重算处理，不因持续入库而一直拒绝发布。
- 九个窗口在同一份 WAL 读快照中计算。结果写入私有临时库，IPC 只传任务参数和完成状态。主进程每个窗口导入后让出事件循环，完成后原子切换批次指针；接口只读内存中的已完成结果，不等待计算。方向响应复用已序列化结果，共振只对汇总信号做筛选。旧批次逐条回收，失败或取消的半批次永不对外可见。
- 子进程堆上限 256 MiB、超时 60 秒；最终结果每个窗口最多 8 MiB、每批最多 32 MiB，超限视为失败，保留上批结果。堆限制不是整机 RSS 上限；统计子进程与原七天观察子进程可能同时运行，仍共享 CPU 和磁盘，不能保证系统完全无延迟。
- 服务重启先加载持久结果；首次无结果时返回 503 预计算提示。计算失败保留上批并标记错误或过期，损坏的派生缓存会从事实库重建。监控新增 `statisticsCompute`；响应新增 `statistics`，包含覆盖时间、输入版本、当前版本、待更新、计算中、过期及错误字段，页面展示统计时间和更新状态。大计算的完成时间、窗口推进周期与前端刷新周期仍会影响结果新鲜度，不能把快速接口响应解释为全部事实都已实时统计。
- 整站重置会清除统计指针和内存结果，并取消旧计算，避免已清空的事实再次被旧批次发布。配置监控名单改变时拒绝读取旧名单的共振批次，随后生成新批次。

验证：后端全套 `node scripts/test-whale-sync.js`（146 个 Node 测试及脚本断言），新增所有窗口及币种筛选的原算法对照、历史修正、窗口自动过期、删除、名单切换、失败和重启恢复、计算期间接口读取、部分导入取消、写入失败、子进程超时及损坏缓存恢复；前端状态与统计读取共 15 个测试、类型检查和构建通过。测试使用隔离临时数据库；本地服务重启后，也验证了后台计算期间两个接口返回已完成结果及待更新标记。

可重复压力基准：`node scripts/benchmark-statistics.js 60000`（仅合成临时库）。一次本机测试中，初次预计算约 3677 ms、追加后的更新约 4900 ms；更新期间 314 次接口请求全部成功，响应 p95 约 9 ms、最大约 19 ms，主线程最大延迟约 23 ms，并对照了完整统计结果。数字受机器负载影响，不代表线上响应或计算时延承诺。部署清单包含三个新增运行文件；发布需前后端同时更新并重启后端。
